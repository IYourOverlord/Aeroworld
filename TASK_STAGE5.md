# ЗАДАЧА: этап 5, чтения соседних секций при построении рендера

Стартовый документ для новой сессии. Сначала прочитать `PROJECT_INDEX.md` (архитектура) и `PROGRESS.md` (статус, журнал, протокол прогонов; особенно разделы «Настройки DH и протокол прогонов», «Этап 4г» и «Этап 5»).

## 1. Правила работы

- Отвечать по-русски, коротко. Числа давать с источником (какое окно лога).
- Каждый ответ с изменениями кода заканчивается zip-архивом изменённых файлов по тем же путям, что в проекте, и вызовом `present_files`. Не создавать `.patch`. Код не показывать только текстом. Файлы, которые нужно удалить у пользователя, называть явно (архив удалять не умеет).
- Ленивый старший разработчик: сначала понять поток данных, искать самое маленькое решение, не писать лишнего. Для нетривиальной логики один запускаемый self-check (assert-демо без фреймворков), упрощения с известным потолком помечать `ponytail:`. Удаление лучше добавления.
- Один этап = одно изменение = один замер. Новые экспериментальные ручки за флагом, по умолчанию выключены. Отвергнутые ручки удалять из проекта (так сделано с этапами 2 и 4г).
- Контейнер: нет gradle и зависимостей NeoForge/DH, полная сборка невозможна. Компилировать так: `java -m jdk.compiler/com.sun.tools.javac.Main -d /tmp/out Файл.java ...`; классы, зависящие от DH, проверять на **заглушках** с теми же сигнатурами (образец: заглушки для `PropagateStatsMixin` из этапа 4г). Байткод: `java -m jdk.jdeps/com.sun.tools.javap.Main -c -cp /tmp/out Класс`. Self-check запускать `java -ea -cp /tmp/out ...SelfCheck`; все существующие (`AeroLeafSlots`, `AeroHybridStats`, `AeroPoolStats`, `AeroPropStats` и др.) должны проходить.
- Первым делом: клонировать `https://github.com/IYourOverlord/Aeroworld`, распаковать присланные архивы исходников DH 3.3.2 (в игре у пользователя DH 3.3.3, имена методов при миксинах сверять и ставить `require = 0`). Пользователь применяет архивы руками: после каждого архива проверять, что все новые файлы дошли.
- В `latest.log` проверять сид (`Level seed ...`), строку `[Environment]` (флаги) и `real radius = 20 chunks` перед любым сравнением. Логи читать в Python с `errors='replace'`.

## 2. Что уже известно (подтверждено кодом DH 3.3.2 и логами)

- Чтения соседей выполняет поток **Render Loader**: `LodRenderSection.getRenderSourceForPos` на каждую секцию делает одно `fullDataSourceProvider.get(pos)` и до четырёх `getAdjForDirection(pos, direction.opposite())`. Внутри один `FullDataSourceV2Repo.getAdjByPosAndDirection(pos, direction)`: `SELECT` одной blob-колонки (`North/South/East/WestAdjData`) и метаданных по `(DetailLevel, PosX, PosZ)`, возвращает закрываемый пулируемый DTO. Строки нет: `getAdjForDirection` возвращает `FullDataSourceV2.createEmpty(pos)` (не `null`); формат V1 мигрирует через `get(pos)`.
- Пул рендера в прогонах занимает 3–6 потоков из 14 (`render` 72–198 задач/с по 31–56 мс), в пике телепорта до 10–11 потоков. Общий пул DH занят на 100%.
- **Существующий `AeroAdjacencyCache` (попаданий 35.8–37.1%, строка `AdjacencyCache Summary`) обслуживает не эти чтения**, а поиск родителей в `StandInTerrainMixin`. Инвалидация уже подключена в `SqliteTuningMixin` (`save`, `deleteWithKey`, `deleteAll`).
- Существующая диагностика `LodRenderSectionAdjDiagMixin` (строка `Adjacent lookups`): в прогонах 2026-10-12 `0 null`, пустых 23–29% (по уровням 12–50%). Она не отличает «строки нет» от «строка есть, боковые данные пустые» и не меряет время.
- Цена чтений соседей **не измерена**. Грубая оценка 4–9% рендера (при 0.5 мс на чтение): выигрыш может уместиться в шум (±9% между одинаковыми прогонами). Поэтому сначала замер.
- Закрытые гипотезы, не возвращаться без новых данных: `saveDelay`, лимит реальных листьев (`dhRealLeafCap`), пропагация (`dhPropagateScale`, `dhPropagateBusyDelayMs`), приоритет Render Loader, подавление каскада в листья (`dhCascadeLeafRadius`), число потоков и `threadRunTimeRatio` (=1.0), очередь выборки `canQueueRetrievalNow`.

## 3. Цель этапа

Выяснить, сколько потоко-времени пула рендера уходит на `getAdjForDirection`, и только если доля существенна, сократить её без изменения визуала.

**Решающее правило** (заложить в журнал до прогона): считать долю = (потоки `adj` из строки замера) / (потоки `render` из строки `Pool`) за окно.
- Доля < 10%: этап 5 закрывается **без кода правки**, замерочный код остаётся за флагом `dhPoolStats` (как `Prop:`) либо удаляется по решению пользователя.
- Доля ≥ 10% и заметная часть чтений «строки нет»: шаг A (отрицательный кэш).
- Доля ≥ 10%, но строки есть и просто боковые данные пустые или читаются повторно: шаг B (положительный кэш копий данных), только если доля повторных чтений одной позиции высока (см. замер).

## 6. Грабли из прошлых этапов

- `require = 0` скрывает неприменённый миксин: подтверждение применения должно быть **отдельной строкой лога для каждой инъекции**.
- `@ModifyConstant` и типы: `Thread.sleep(INT)` компилируется в long-константу; проверять байткод тестовым классом через `javap -c`.
- `Set.add` в `@Redirect` это `INVOKEINTERFACE java/util/Set.add:(Ljava/lang/Object;)Z`, обработчик принимает `(Set<Object>, Object)`; лямбды внутри целевого метода имеют отдельные синтетические методы и в `@Redirect(method=...)` не попадают.
- Нельзя два `@Redirect` на одно место вызова (конфликт миксинов): измерение и поведение держать в одном обработчике.
- Измерительная логика должна быть чистой (без MC/DH), чтобы проверяться self-check в контейнере.
- Итог `Total chunks` на момент конца нельзя сравнивать между прогонами (артефакт момента печати окна); время конца считать по `BacklogGate`.
- У тестировщика лок FPS: критерии по FPS недоступны, оценивать по логу.
