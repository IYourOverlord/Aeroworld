# PROGRESS — оптимизация прогрузки мира через Distant Horizons

Цель: приблизить скорость прогрузки LOD (DH 3.3.2) к «тысячам чанков/с» без заметной потери визуала и без просадки FPS.
Основа: сравнение с SeedGen 0.8.0 (8 пунктов) + сверка с исходниками DH 3.3.2.

**Правила работы**

1. Один этап = одно изменение = один замер. Не смешивать этапы в одном прогоне.
2. Каждое новое поведение включается флагом (`-Daeroworld.dh<Имя>` и/или ключ в `AeroWorldConfig`, как уже сделано для `dhBorder`, `dhTwoPhase`). Флаг выключен → поведение как сейчас.
3. Код SeedGen не переносится. Берётся только идея; реализация своя, на своих именах и на существующих паттернах Aeroworld (`AeroThroughputLimits`, `AeroHybridStats`, `*SelfCheck`).
4. Не готово, пока нет: замера «до/после», проверки визуала по контрольным точкам, отката через флаг.
5. Приоритет: корректность > сборка > консистентность > скорость (как в общих правилах проекта).

## Что отсеяно после сверки с DH 3.3.2

Эти два пункта из первоначального сравнения в 3.3.2 уже не дают выигрыша. Не делать.

- **Пункт 2 (константа 20 в `canQueueRetrievalNow`).** В 3.3.2 `canQueueRetrievalNow` берёт лимит из `getMaxRetrievalQueueCount()`, а константа `MAX_RETRIEVAL_REQUESTS_PER_THREAD = 20` вшита именно туда. Её уже масштабирует `RetrievalQueueLimitMixin` (QUEUE_SCALE = 4). Остаётся только проверить, что дополнительные условия того же метода не режут очередь (этап 4).
- **Пункт 3, часть про приоритет планировщика.** В 3.3.2 `PriorityTaskPicker` сначала сортирует исполнителей по `priority` (Render Loader 6 выше World Gen 5), и только потом по времени работы. Рендер и так обслуживается первым. Отдельный миксин приоритета не нужен.

- [ ] Записывать на каждый прогон: чанки/с на экране DH; внутренний accept-rate (строка `Throughput` из `AeroThroughputLimits`); срез `AeroWorld-GateDiagnostics`; строки `[Regen]` из `AeroHybridStats`; средний и худший кадр (F3) в первые 60 с.

- [ ] Занести результат в таблицу в конце этого файла (раздел «Журнал замеров»).

## Этап 1. Реже и умнее сохранять LOD на диск (пункт 6)

**Проблема.** `AeroThroughputLimits.SAVE_DELAY_MS = 1000`, штатное значение DH 10000. Секция, которую DH обновляет серией дочерних записей, сохраняется в 10 раз чаще.

**Свой подход.** Не просто вернуть 10000, а сделать задержку настраиваемой и безопасной для данных.

**Шаги**

- [ ] Вынести задержку в ключ `AeroWorldConfig` (например `DH_SAVE_DELAY_MS`) с переопределением `-Daeroworld.dhSaveDelayMs`. По умолчанию для замера: 10000.
- [ ] Гарантия сохранности: при выходе из мира и при остановке сервера выполнять принудительный сброс (проверить, что DH делает это сам; если нет, добавить вызов flush в обработчик остановки уровня). Периодический `wal_checkpoint` в `SqliteTuningMixin` уже есть, оставить.
- [ ] Прогнать этап 0 с 10000, затем с 3000. Выбрать значение, после которого скорость перестаёт расти.

**Файлы:** `AeroThroughputLimits.java`, `SaveDelayMixin.java`, `AeroWorldConfig.java`.
**Баланс.** Визуал не меняется. Риск: потеря последних секунд генерации при аварийном завершении. Для аналитического генератора это безвредно, секции пересчитываются по сиду.
**Откат:** значение 1000.

## Этап 2. Пропагация LOD вверх по иерархии (пункт 1)

**Проблема.** Ваши внутренние числа выше экранных, то есть часть работы уходит ниже по течению: `FullDataUpdatePropagatorV2` строит родительские уровни. Сейчас у вас в этом классе только статистический `RegenGateStatsMixin`.

**Что есть в DH 3.3.2** (проверено): `getMaxPropagateTaskCount()` = 10 задач на поток; цикл `runUpdateQueue` спит 250 мс между проходами (`PROPAGATE_QUEUE_THREAD_DELAY_IN_MS`, int).

**Свой подход.** Две независимые ручки, каждая со своим флагом, и адаптивность вместо фиксированного значения.

**Шаги**

- [ ] Ручка A, лимит задач: миксин на возврат `getMaxPropagateTaskCount()` с множителем из `AeroThroughputLimits` (начать с 2, затем 4). Статический метод, поведение как у уже работающего `RetrievalQueueLimitMixin`.
- [ ] Ручка B, пауза между проходами: цель константа `PROPAGATE_QUEUE_THREAD_DELAY_IN_MS` (тип `int`, значение 250). Сделать пауза зависящей от нагрузки: пока идёт интенсивная генерация, 500 мс; когда очередь пуста, обратно 250 мс, чтобы грубые LOD у игрока обновлялись быстро. Адаптивность нужна, потому что DH специально обновляет позиции рядом с игроком первыми, «чтобы генерация выглядела быстрее».
- [ ] Выставить `require = 0`, чтобы смена версии DH не роняла игру, и залогировать одну строку при инициализации, применился ли миксин.
- [ ] Прогнать этап 0 для A отдельно, для B отдельно, затем вместе.

**Файлы:** новый `PropagateLimitsMixin.java` в `mixin/dh/`, запись в `aeroworld.mixins.json`, `AeroThroughputLimits.java`.
**Баланс.** Больше задач: выше нагрузка на ядра (вы уже видели, что слепое увеличение concurrency ухудшает скорость, см. IN_FLIGHT_SCALE 16). Поэтому начинать с ×2 и смотреть на оба числа (экран и accept-rate). Пауза больше 500 мс: родительские LOD появляются с запаздыванием, проверить на скриншотах «горизонт».
**Откат:** флаги в 1 и 250.

## Этап 3. Бюджет загрузки в GPU без просадки FPS (пункт 3, оставшаяся часть)

**Что есть в DH 3.3.2.** `RenderThreadTaskHandler.runRenderThreadTasks()` отдаёт на загрузку в GPU половину времени кадра (по лимиту кадров, 240 по умолчанию). При большой очереди это узкое место видимой прогрузки.

**Свой подход.** Не фиксированный множитель, а бюджет, зависящий от длины очереди и от текущей частоты кадров.

**Шаги**

- [ ] Миксин вокруг расчёта доли кадра в `runRenderThreadTasks()`: множитель 1 при короткой очереди, растёт до потолка (начать с ×3) при длинной.
- [ ] Защита от просадки: если предыдущий кадр дольше порога (например 25 мс), множитель падает до 1 на следующие несколько кадров.
- [ ] Порог очереди использовать тот же, что уже читает `WorldGenSpeedGateMixin` (`renderYieldQueue`), чтобы не плодить настройки.
- [ ] Замер: чанки/с, но главное — худший кадр в первые 60 с (F3). Любое ухудшение худшего кадра выше 25 мс = снижать потолок.
- [ ] Приоритет планировщика отдельно не трогать (см. «Что отсеяно»).

**Файлы:** новый `RenderUploadBudgetMixin.java`, `aeroworld.mixins.json`, `AeroThroughputLimits.java`.
**Баланс.** Это единственный этап, где скорость можно купить ценой плавности. Потолок и порог кадра задают баланс.
**Откат:** флаг в 1.

## Этап 4. Очередь выборки: проверка, а не правка (пункт 2)

**Зачем.** Отсеянная константа уже масштабирована. Но `canQueueRetrievalNow` в 3.3.2 имеет и другие условия отказа: суммарная очередь `WorldChunkUpdateManager`, число несохранённых секций (при превышении лимита делается flush), число свободных слотов.

**Шаги**

- [ ] Взять данные из существующего `CanQueueStatsMixin` / `AeroHybridStats` (строка `canQueueRetrievalNow:... avg waiting ... of max`) на этапах 1–3.
- [ ] Если отказ идёт по условию «несохранённых секций ≥ лимит», это связано с этапом 1: при задержке 10000 оно может срабатывать чаще. Тогда выбрать компромисс между этапом 1 и лимитом, а не повышать лимит.
- [ ] Если отказ идёт по очереди обновления чанков, источником является реальная генерация листьев в радиусе R (гибрид), это тема этапа 7 и радиуса R, а не очереди.
- [ ] Решение записать в журнал; код менять только если замер показывает конкретное условие.

**Готово, когда:** в журнале указано, какое условие чаще всего блокирует очередь, и что с ним решено.

## Этап 5. Соседние секции из памяти (пункт 4)

**Проблема.** `AeroAdjacencyCache` (ключи `DH_ADJACENCY_CACHE_*` уже есть в конфиге) используется только внутри `StandInTerrainMixin`. Обычный путь рендера читает соседей напрямую из SQLite: `FullDataSourceProviderV2` вызывает `repo.getAdjByPosAndDirection(pos, direction)`, возвращая закрываемый `FullDataSourceV2DTO`.

**Свой подход.** Двухшаговый, от безопасного к рискованному. Закрываемый пулируемый DTO нельзя класть в кэш как есть: им владеет вызывающий.

**Шаги**

- [ ] Шаг A, отрицательный кэш: миксин на `FullDataSourceV2Repo.getAdjByPosAndDirection` в начале метода: если позиция соседа помечена «в БД нет», вернуть `null` без запроса. Метку ставить по результату запроса; снимать в уже существующих хуках `save` / `deleteWithKey` / `deleteAll` в `SqliteTuningMixin` (там уже вызывается `AeroAdjacencyCache.invalidate`). Это самый частый случай на фронте генерации и не требует хранить данные.
- [ ] Шаг B, положительный кэш, только если замер после шага A покажет много повторных чтений: хранить не сам DTO, а независимую копию его данных с коротким временем жизни (`DH_ADJACENCY_CACHE_TTL_SEC`), отдавать каждый раз новый DTO. Размер ограничен `DH_ADJACENCY_CACHE_SIZE`.
- [ ] Один runnable-чек (по образцу `AeroLeafLedgerSelfCheck`): запись секции → чтение соседа → повторная запись → чтение даёт новые данные (проверка инвалидации).
- [ ] Лог итогов через существующий `AeroAdjacencyCache.logSummary()`: хиты/промахи.

**Файлы:** новый `AdjacencyRepoMixin.java`, `AeroAdjacencyCache.java` (добавить отрицательные метки), `aeroworld.mixins.json`.
**Баланс.** Визуал не меняется. Риск устаревших данных: закрывается инвалидацией и коротким TTL.
**Откат:** `DH_ADJACENCY_CACHE_ENABLED=false`.

## Этап 6. Прямая запись колонок в секцию DH (пункт 5)

**Что происходит сейчас.** Для каждой колонки: `List<AeroColumnModel.Span>` → `List<DhApiTerrainDataPoint>` (новые объекты на каждый спан, `AeroColumnWriter.toDataPoints`) → `setApiDataPointColumn`, который внутри упорядочивает список, при включённой проверке валидирует, упаковывает в `LongArrayList` и вызывает `setSingleColumn(..., MERGE_SAME_BLOCKS)`.

**Свой подход.** Пропустить промежуточные объекты, а упаковку сделать теми же средствами DH.

**Шаги**

- [ ] Сначала профиль: доля времени `toDataPoints` + `setApiDataPointColumn` в задаче d0. Если меньше ~15%, этап не делать, выигрыш не оправдает риск.
- [ ] В `AeroColumnWriter` добавить метод записи колонки прямо в `FullDataSourceV2` (источник доступен как реальный класс за `IDhApiFullDataSource`): для каждого спана получить id через `mapping.addIfNotPresentAndGetId(biome, block)`, упаковать в переиспользуемый `LongArrayList` (по одному на поток), вызвать `setSingleColumn` с тем же шагом генерации и `MERGE_SAME_BLOCKS`.
- [ ] Порядок спанов и границы (`topY` исключающий, воздух в пустотах, сверху вниз) взять из текущего `toDataPoints`, чтобы результат был идентичным.
- [ ] Включение по флагу `-Daeroworld.dhDirectWrite`. Старый путь остаётся рабочим при выключенном флаге или если приведение типа не удалось.
- [ ] Один runnable-чек: для N случайных колонок старый и новый путь дают одинаковые `LongArrayList`.

**Файлы:** `AeroColumnWriter.java`, `AeroSeedWorldGenerator.java` (две точки вызова), новый `AeroColumnWriterSelfCheck.java`.
**Баланс.** Визуал идентичен по построению (проверяется чеком). Риск: привязка к внутренним классам DH, поэтому флаг и fallback.
**Откат:** флаг выключен.

## Этап 7. Дешевле дальние уровни с контролем визуала (пункт 7)

**Что уже есть.** `AeroFastDistantTerrain` (пороги слоёв 2–4, число подвыборок по `detailLevel`), `AeroStructureMarkers.MAX_DETAIL`, `AeroTreeCover` в `AeroColumnModel`.

**Свой подход.** Менять по одной ручке и каждый раз сравнивать скриншоты контрольных точек.

**Шаги**

- [ ] Деревья/растительность в LOD: отключать при ширине колонки больше порога (начать с 4 блоков). Проверить лес и `wisteria_grove`.
- [ ] Миниатюры структур: проверить, что `MAX_DETAIL` не выше нужного, и посмотреть стоимость `AeroStructureMarkers.forSection` в профиле задачи.

- [ ] Пороги слоёв `layer2/3/4DetailThreshold`: по замеру времени задач по уровням (в логе `analytic tasks by detail`) найти уровень, где задача заметно дороже соседних, и снизить сложность только там.

## Этап 8. Рендер-нагрузка: отложено

SeedGen переносит построение боковых граней на GPU (compute). Для Aeroworld это не рекомендуется сейчас: слишком хрупко к версии DH, драйверам и режимам рендера, и выигрыш виден только на рендер-стороне.

**Критерий возврата:** после этапов 1–7 очередь Render Loader остаётся стабильно длинной (выше `renderYieldQueue`) при свободных ядрах.
**Лёгкая альтернатива, если критерий выполнится:** в рамках мода уменьшать число боковых граней у дальних секций (по расстоянию), без GPU-кода; ориентиры: `TranslucentAdjWallMixin`, `LodRenderSectionAdjDiagMixin`.
