# PROGRESS — оптимизация прогрузки мира через Distant Horizons

Цель: приблизить скорость прогрузки LOD (DH 3.3.2) к «тысячам чанков/с» без заметной потери визуала и без просадки FPS.
Основа: сравнение с SeedGen 0.8.0 (8 пунктов) + сверка с исходниками DH 3.3.2.

**Правила работы**

1. Один этап = одно изменение = один замер. Не смешивать этапы в одном прогоне.
2. Каждое новое поведение включается флагом (`-Daeroworld.dh<Имя>` и/или ключ в `AeroWorldConfig`, как уже сделано для `dhBorder`, `dhTwoPhase`). Флаг выключен → поведение как сейчас.
3. Код SeedGen не переносится. Берётся только идея; реализация своя, на своих именах и на существующих паттернах Aeroworld (`AeroThroughputLimits`, `AeroHybridStats`, `*SelfCheck`).
4. Не готово, пока нет: замера «до/после», проверки визуала по контрольным точкам, отката через флаг.
5. Приоритет: корректность > сборка > консистентность > скорость (как в общих правилах проекта).

**Свой подход.** Не менять поведение по умолчанию, а сделать задержку настраиваемой и сравнить.

**Шаги**

- [x] Задержка читается из системного свойства `-Daeroworld.dhSaveDelayMs=N` (диапазон 250..30000, по умолчанию 1000, как раньше). Это свойство, а не ключ `AeroWorldConfig`: значение нужно при создании провайдера, до загрузки конфига. Значение пишется в строку `[Environment]` лога, чтобы каждый прогон было видно, с чем он сделан.

## Этап 5. Соседние секции из памяти (пункт 4)

**Проблема.** `AeroAdjacencyCache` (ключи `DH_ADJACENCY_CACHE_*` уже есть в конфиге) используется только внутри `StandInTerrainMixin`. Обычный путь рендера читает соседей напрямую из SQLite: `FullDataSourceProviderV2` вызывает `repo.getAdjByPosAndDirection(pos, direction)`, возвращая закрываемый `FullDataSourceV2DTO`.

**Свой подход.** Двухшаговый, от безопасного к рискованному. Закрываемый пулируемый DTO нельзя класть в кэш как есть: им владеет вызывающий.

**Шаги**

- [ ] Шаг A, отрицательный кэш: миксин на `FullDataSourceV2Repo.getAdjByPosAndDirection` в начале метода: если позиция соседа помечена «в БД нет», вернуть `null` без запроса. Метку ставить по результату запроса; снимать в уже существующих хуках `save` / `deleteWithKey` / `deleteAll` в `SqliteTuningMixin` (там уже вызывается `AeroAdjacencyCache.invalidate`). Это самый частый случай на фронте генерации и не требует хранить данные.
- [ ] Шаг B, положительный кэш, только если замер после шага A покажет много повторных чтений: хранить не сам DTO, а независимую копию его данных с коротким временем жизни (`DH_ADJACENCY_CACHE_TTL_SEC`), отдавать каждый раз новый DTO. Размер ограничен `DH_ADJACENCY_CACHE_SIZE`.
- [ ] Один runnable-чек (по образцу `AeroLeafLedgerSelfCheck`): запись секции → чтение соседа → повторная запись → чтение даёт новые данные (проверка инвалидации).
- [ ] Лог итогов через существующий `AeroAdjacencyCache.logSummary()`: хиты/промахи.

**Файлы:** новый `AdjacencyRepoMixin.java`, `AeroAdjacencyCache.java` (добавить отрицательные метки), `aeroworld.mixins.json`.
**Баланс.** Визуал не меняется. Риск устаревших данных: закрывается инвалидацией и коротким TTL.
**Откат:** `DH_ADJACENCY_CACHE_ENABLED=false`.

## Этап 6. Прямая запись колонок в секцию DH (пункт 5)

**Что происходит сейчас.** Для каждой колонки: `List<AeroColumnModel.Span>` → `List<DhApiTerrainDataPoint>` (новые объекты на каждый спан, `AeroColumnWriter.toDataPoints`) → `setApiDataPointColumn`, который внутри упорядочивает список, при включённой проверке валидирует, упаковывает в `LongArrayList` и вызывает `setSingleColumn(..., MERGE_SAME_BLOCKS)`.

**Свой подход.** Пропустить промежуточные объекты, а упаковку сделать теми же средствами DH.

**Шаги**

- [ ] Сначала профиль: доля времени `toDataPoints` + `setApiDataPointColumn` в задаче d0. Если меньше ~15%, этап не делать, выигрыш не оправдает риск.
- [ ] В `AeroColumnWriter` добавить метод записи колонки прямо в `FullDataSourceV2` (источник доступен как реальный класс за `IDhApiFullDataSource`): для каждого спана получить id через `mapping.addIfNotPresentAndGetId(biome, block)`, упаковать в переиспользуемый `LongArrayList` (по одному на поток), вызвать `setSingleColumn` с тем же шагом генерации и `MERGE_SAME_BLOCKS`.
- [ ] Порядок спанов и границы (`topY` исключающий, воздух в пустотах, сверху вниз) взять из текущего `toDataPoints`, чтобы результат был идентичным.
- [ ] Включение по флагу `-Daeroworld.dhDirectWrite`. Старый путь остаётся рабочим при выключенном флаге или если приведение типа не удалось.
- [ ] Один runnable-чек: для N случайных колонок старый и новый путь дают одинаковые `LongArrayList`.

**Файлы:** `AeroColumnWriter.java`, `AeroSeedWorldGenerator.java` (две точки вызова), новый `AeroColumnWriterSelfCheck.java`.
**Баланс.** Визуал идентичен по построению (проверяется чеком). Риск: привязка к внутренним классам DH, поэтому флаг и fallback.
**Откат:** флаг выключен.

## Этап 7. Дешевле дальние уровни с контролем визуала (пункт 7)

**Что уже есть.** `AeroFastDistantTerrain` (пороги слоёв 2–4, число подвыборок по `detailLevel`), `AeroStructureMarkers.MAX_DETAIL`, `AeroTreeCover` в `AeroColumnModel`.

**Свой подход.** Менять по одной ручке и каждый раз сравнивать скриншоты контрольных точек.

**Шаги**

- [ ] Деревья/растительность в LOD: отключать при ширине колонки больше порога (начать с 4 блоков). Проверить лес и `wisteria_grove`.
- [ ] Миниатюры структур: проверить, что `MAX_DETAIL` не выше нужного, и посмотреть стоимость `AeroStructureMarkers.forSection` в профиле задачи.
- [ ] Подвыборки `subsamplesForDetailLevel`: попробовать уменьшить на одну ступень для detail ≥ 3. Контроль: берег, плато, горы.
- [ ] Пороги слоёв `layer2/3/4DetailThreshold`: по замеру времени задач по уровням (в логе `analytic tasks by detail`) найти уровень, где задача заметно дороже соседних, и снизить сложность только там.
- [ ] Эксперимент, отдельно и в самом конце: `getLargestDataDetailLevel()`. Сейчас `REGION`. Повышение уменьшает число секций верхних уровней, но DH считает `lowestDataDetailLevel = 6 + largest`. Менять только с A/B на чистом мире.

**Файлы:** `AeroFastDistantTerrain.java`, `AeroSeedWorldGenerator.java`, `DhOverrideSettings.java`.
**Баланс.** Здесь визуал страдает первым. Правило: если по скриншоту разница видна на нормальной дальности, изменение откатывается.
**Откат:** возврат прежних значений порогов.

## Этап 8. Рендер-нагрузка: отложено

SeedGen переносит построение боковых граней на GPU (compute). Для Aeroworld это не рекомендуется сейчас: слишком хрупко к версии DH, драйверам и режимам рендера, и выигрыш виден только на рендер-стороне.

**Критерий возврата:** после этапов 1–7 очередь Render Loader остаётся стабильно длинной (выше `renderYieldQueue`) при свободных ядрах.
**Лёгкая альтернатива, если критерий выполнится:** в рамках мода уменьшать число боковых граней у дальних секций (по расстоянию), без GPU-кода; ориентиры: `TranslucentAdjWallMixin`, `LodRenderSectionAdjDiagMixin`.
